# [요구사항 정의서] 원본 요청 상품 옵션 식별 체계 개선

## 1. 문서 목적

상품의 실제 판매·재고 단위마다 바뀌지 않는 식별 코드(옵션코드)가 왜 필요한지, 무엇을 만족해야 하는지 정리합니다. 상세 정책은 정책서, 기능·수용 조건은 사양 정의서에서 관리합니다.

## 2. 요청 배경 및 목표

### 2.1. 요청 배경

- 고객이 실제로 사는 것은 "티셔츠"가 아니라 "블랙 티셔츠 XS"입니다. 실제 판매 단위는 조합옵션(옵션이 정해진 품목)이고, 상품명·판매가는 판매 단위를 감싸는 공통 정보입니다.
- 그런데 판매 단위에는 바뀌지 않는 식별자가 없습니다. 재고, 재입고 알림, 통합 엑셀처럼 옵션을 번호로 기억하는 기능이 같은 판매 단위를 계속 정확하게 가리킬 수 없습니다.

### 2.2. 운영·시스템이 필요한 결과

- 판매 단위마다 바뀌지 않는 옵션코드가 있어야 합니다.
- 옵션을 수정·재조합해도 같은 판매 단위는 같은 코드여야 하고, 한 번 쓴 코드는 다른 판매 단위에 다시 쓰이지 않아야 합니다.
- 운영자가 화면에서 코드를 확인하고 코드로 검색할 수 있어야 합니다.

## 3. 현행 기능 및 해결 과제

### 3.1. 현행 식별 구조

| 식별값 | 단위 | 현행 동작 |
|---|---|---|
| 상품번호 | 상품 | 상점 안에서 유일하고 바뀌지 않습니다. |
| 조합 순번 | 조합옵션 | 상품 안의 순번입니다. 옵션을 수정·재조합하면 저장된 조합을 지우고 다시 만들어 번호가 바뀌고, 지운 번호가 다시 쓰일 수 있습니다. |
| 관리코드 | 조합옵션 | 운영자가 직접 입력하는 값입니다. 비어 있거나 중복될 수 있어 식별자로 쓸 수 없습니다. |
| 없음 | 미조합 옵션·옵션 없는 상품 | 판매 단위를 가리킬 번호가 없습니다. |

### 3.2. 문제 원인

- 판매 단위의 식별값(조합 순번)이 저장할 때마다 다시 만들어집니다.
- 지운 번호를 재사용하지 않는다는 보장이 없습니다.

### 3.3. 문제 예시

| 순서 | 운영자 작업 | 현행 결과 | 영향 |
|---|---|---|---|
| 1 | 블랙/XS에 재입고 알림이 걸림 | 블랙/XS = 번호 3 | |
| 2 | 화이트 색상을 추가해 재조합 | 저장된 조합을 다시 만들면서 블랙/XS 번호가 바뀔 수 있음 | 번호 3으로 건 알림이 블랙/XS를 찾지 못함 |
| 3 | 블랙/XS를 지우고 다른 조합 추가 | 지운 번호 3이 새 조합에 다시 쓰일 수 있음 | 블랙/XS 알림이 다른 옵션으로 연결됨 |

## 4. 요구사항

| REQ ID | 요구사항 | 필수 여부 |
|---|---|---|
| REQ-001 | 판매 단위마다 바뀌지 않는 옵션코드가 있어야 합니다. | 필수 |
| REQ-002 | 옵션을 수정·재조합해도 같은 판매 단위는 같은 코드를 유지하고, 지운 코드는 다시 쓰지 않아야 합니다. | 필수 |
| REQ-003 | 이미 등록된 상품도 배포 시점부터 옵션코드가 있어야 합니다. | 필수 |
| REQ-004 | 운영자가 관리자 화면에서 옵션코드를 확인할 수 있어야 합니다. | 필수 |
| REQ-005 | 운영자가 옵션코드로 상품과 재입고 알림 내역을 찾을 수 있어야 합니다. | 필수 |

## 5. 대표 사용자 시나리오

### 5.1. 상점 운영 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 티셔츠(블랙 S·M·L)에 화이트 색상을 추가 | 블랙 3개 코드는 그대로이고 화이트 3개에만 새 코드 |
| 관리자 화면에서 블랙을 다크블랙으로 이름 변경 | 코드 유지 |
| 상품을 실수로 삭제했다가 복구 | 삭제 전 코드 그대로, 재입고 알림 연결 유지 |
| 재입고 알림 관리에서 특정 옵션의 코드로 검색 | 그 옵션의 알림 내역만 표시 |

### 5.2. 고객 구매 흐름

구매자 화면과 주문 흐름은 바뀌지 않습니다.

## 6. 구현 방향 검토

### 6.1. 대안 비교

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 조합 순번가 바뀌지 않게 저장 방식 변경 | 기존 저장 로직 전면 수정 | 기존 기능 회귀 위험이 커서 채택하지 않음 |
| B. 관리코드를 식별자로 사용 | 운영자 입력값 | 비어 있거나 중복될 수 있어 채택하지 않음 |
| C. 새 옵션코드를 하나 더 추가 | 기존 값은 그대로 두고 시스템 발급 코드 추가 | 채택 |

### 6.2. 검토 방향

- 기존 식별값과 기능은 그대로 두고 옵션코드만 추가합니다.
- 형식은 `{상품번호}-{4자리 순번}`이며 하이픈을 항상 넣습니다. 하이픈 없이 붙이면 자릿수가 늘어날 때 코드가 겹치고 엑셀에서 숫자로 깨질 수 있습니다.
- 재고가 관리되는 행 1개에 코드 1개를 발급합니다.

## 7. 기능 범위

| 구분 | 내용 |
|---|---|
| 포함 | 옵션코드 발급·유지·종료, 상품 복사·삭제·복구 처리, 기존 상품 일괄 발급, 옵션 팝업 3종·상품 수정 요약 박스 표시, 상품 메뉴 4개 화면 검색 |
| 제외 | 다중 상품 옵션 불러오기(결정 대기), 상품 엑셀(통합 엑셀 프로젝트 관련 Task), 주문 메뉴(추후), Open API, 옵션 순서 변경·조합 상한 등 옵션 기능 개선, 기존 주문 데이터 |

## 8. 영향 영역

| 영역 | 영향 |
|---|---|
| 상품 등록·수정 | 옵션 저장 시 옵션코드 발급·유지 판정 추가 |
| 옵션 팝업(기본옵션·하이브리드·개별옵션) | 옵션코드 열 추가 |
| 전체 상품 관리·삭제 상품 조회·재고 일괄 관리·재입고 알림 관리 | 검색 항목 추가 |
| 상품 복사·삭제·복구 | 옵션코드 처리 추가 |
| 후속 과제 | 통합 엑셀(관련 Task)·재입고 알림(관련 Task)이 옵션코드 사용 |

## 9. 정책 검토 항목

| 항목 | 결정 | 정리 위치 |
|---|---|---|
| 발급 단위 | 재고 행 1개 = 코드 1개(조합마다, 미조합·옵션 없음은 상품당, 하이브리드·개별옵션은 옵션값마다, 원클릭은 별도 없음) | 정책서 4.1 |
| 형식·순번 | `{상품번호}-{순번}`, 최소 4자리, 종료 번호 재사용 없음, 상품 안에서 한 순번 공유 | 정책서 4.2 |
| 유지·신규·종료 | 같은 판매 단위면 유지, 새 단위만 신규, 구조 변경·유형 전환은 전체 신규 | 정책서 4.3 |
| 목록 표시 순서 | 조합·개별옵션은 코드 순, 하이브리드는 운영자 순서 | 정책서 4.2 |
| 검색 | 4개 화면, 완전 일치 | 정책서 4.7 |
| 다중 상품 옵션 불러오기 | 결정 대기 | 사양 정의서 OPEN-001 |
