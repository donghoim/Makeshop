# [요구사항 정의서] 원본 요청 상품 옵션 식별 체계 개선

## 1. 문서 목적

상품의 실제 판매·재고 단위마다 바뀌지 않는 식별 코드(옵션코드)가 왜 필요한지, 무엇을 만족해야 하는지 정리합니다. 상세 정책은 정책서, 기능·수용 조건은 사양 정의서에서 관리합니다.

## 2. 요청 배경 및 목표

### 2.1. 요청 배경

- 고객이 실제로 사는 것은 "티셔츠"가 아니라 "블랙 티셔츠 XS"입니다. 실제 판매 단위는 옵션이 정해진 품목이고, 상품명·판매가는 판매 단위를 감싸는 공통 정보입니다.
- 판매 단위마다 내부 번호는 있지만 운영자가 볼 수 없고, 지운 번호가 다른 옵션에 다시 쓰일 수 있습니다. 재고, 재입고 알림, 통합 엑셀처럼 옵션을 번호로 기억하는 기능이 같은 판매 단위를 계속 정확하게 가리킬 수 없습니다.

### 2.2. 운영·시스템이 필요한 결과

- 판매 단위마다 바뀌지 않는 옵션코드가 있어야 합니다.
- 옵션을 수정·재조합해도 같은 판매 단위는 같은 코드여야 하고, 한 번 쓴 번호는 다른 판매 단위에 다시 쓰이지 않아야 합니다.
- 운영자가 화면에서 코드를 확인하고 코드로 검색할 수 있어야 합니다.
- 재조합할 때 같은 조합의 재고·상태를 유지할지 운영자가 고를 수 있어야 합니다.

## 3. 현행 기능 및 해결 과제

### 3.1. 현행 식별 구조

| 식별값 | 단위 | 현행 동작 |
|---|---|---|
| 상품번호 | 상품 | 상점 안에서 유일하고 바뀌지 않습니다. |
| 조합 순번 | 판매 단위(재고 행) | 상품 안의 번호입니다. 옵션 없음·미조합 상품도 1개씩 있고, 네이버페이·Open API가 이 번호를 씁니다. 화면에는 보이지 않습니다. 가장 큰 번호의 옵션을 지우거나 옵션 사용 안 함으로 바꾸면 같은 번호를 다시 씁니다. |
| 관리코드 | 조합옵션 | 운영자가 직접 입력하는 값입니다. 비어 있거나 중복될 수 있어 식별자로 쓸 수 없습니다. |

### 3.2. 문제 원인

- 판매 단위 번호를 운영자가 볼 수 없어 코드로 가리킬 수 없습니다.
- 지운 번호를 다시 쓰지 않는다는 보장이 없습니다.
- 일반 상점은 재조합하면 같은 조합도 재고·상태가 초기화되고, 일부 특별처리 상점만 기존 데이터를 가져올지 고를 수 있습니다.

### 3.3. 문제 예시

| 순서 | 운영자 작업 | 현행 결과 | 영향 |
|---|---|---|---|
| 1 | 블랙/L에 재입고 알림이 걸림 | 블랙/L = 번호 5(가장 큰 번호) | |
| 2 | 블랙/L을 지우고 저장 | 번호 5가 비게 됨 | |
| 3 | 새 조합 화이트/XL을 추가 | 지운 번호 5가 화이트/XL에 다시 쓰일 수 있음 | 블랙/L로 건 알림이 화이트/XL에 연결됨 |

|---|---|---|
| REQ-001 | 판매 단위마다 바뀌지 않는 옵션코드가 있어야 합니다. | 필수 |
| REQ-002 | 옵션을 수정·재조합해도 같은 판매 단위는 같은 코드를 유지하고, 지운 번호는 다시 쓰지 않아야 합니다. | 필수 |
| REQ-003 | 이미 등록된 상품도 배포 시점부터 옵션코드가 있어야 합니다. | 필수 |
| REQ-004 | 운영자가 관리자 화면에서 옵션코드를 확인할 수 있어야 합니다. | 필수 |

| REQ-006 | 재조합할 때 같은 옵션 조합의 기존 데이터를 유지할지 운영자가 고를 수 있어야 합니다. | 필수 |

## 5. 대표 사용자 시나리오

### 5.1. 상점 운영 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 티셔츠(블랙 S·M·L)에 화이트 색상을 추가해 재조합 | 확인창에서 기존 데이터 유지·초기화를 고름. 어느 쪽이든 블랙 3개 코드는 그대로이고 화이트 3개에만 새 코드 |
| 관리자 화면에서 블랙을 다크블랙으로 이름 변경 | 화이트 조합은 유지, 다크블랙 조합은 새 코드(입력 안내로 미리 알림) |
| 블랙/L을 지우고 저장한 뒤 새 조합 추가 | 지운 번호를 다시 쓰지 않고 다음 번호 |
| 상품을 실수로 삭제했다가 복구 | 삭제 전 코드 그대로 |
| 전체 상품 관리에서 상품번호나 옵션코드로 검색 | 해당 상품 표시 |

### 5.2. 고객 구매 흐름

구매자 화면과 주문 흐름은 바뀌지 않습니다.

## 6. 구현 방향 검토

### 6.1. 대안 비교

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 새 옵션코드 체계 추가 | 기존 번호와 별도로 시스템이 새 코드를 발급 | 판매 단위 번호가 이미 있어 같은 역할의 값이 두 개가 되므로 채택하지 않음(개발 검토 관련 Task) |
| B. 관리코드를 식별자로 사용 | 운영자 입력값 | 비어 있거나 중복될 수 있어 채택하지 않음 |
| C. 기존 판매 단위 번호를 옵션코드로 노출 | 기존 번호를 형식에 맞춰 보여 주고 재사용만 막음 | 채택 |

### 6.2. 검토 방향

- 기존 식별값과 연동은 그대로 두고, 판매 단위 번호를 옵션코드로 보여 줍니다.
- 형식은 `M{상품번호}-{9자리 순번}`입니다(예: `M123456789-000000001`). 기존에 일부 상점이 쓰던 형식을 전체 상점에 적용합니다. 순번이 999999999를 넘으면 자릿수가 늘어납니다.
- 재고가 관리되는 행 1개에 코드 1개입니다.

## 7. 기능 범위

| 구분 | 내용 |
|---|---|
| 포함 | 옵션코드 노출·유지·종료, 재조합 확인창(버튼 3개), 상품 복사·삭제·복구 처리, 옵션 팝업 3종·상품 수정 요약 박스·옵션별 재고 수정 팝업 표시, 상품 메뉴 3개 화면 검색, Open API 조회, 특별처리 상점 정리 |
| 제외 | 상품 엑셀(통합 엑셀 프로젝트 관련 Task), 재입고 알림 관리 검색, 다중 상품 옵션 불러오기, 관리자앱, 주문 메뉴(추후), Open API 수정, 개별옵션 순서 값 오류(관련 Task과 후속), 기존 주문 데이터 |

## 8. 영향 영역

| 영역 | 영향 |
|---|---|
| 상품 등록·수정 | 옵션 저장 시 유지·새 부여 판정, 번호 재사용 방지 |
| 옵션 팝업(기본옵션·하이브리드·개별옵션) | 옵션코드 열 추가(맨 앞), 옵션값 입력 안내 추가 |
| 옵션 재조합 | 확인창을 레이어 팝업(버튼 3개)으로 변경, 특별처리 상점은 기존 확인창 유지 |
| 전체 상품 관리·삭제 상품 조회·재고 일괄 관리 | 검색 항목 추가, 옵션별 재고 수정 팝업에 열 추가 |
| 상품 복사·삭제·복구 | 옵션코드 처리 |
| Open API | 조회 응답에 옵션코드 추가 |
| 후속 과제 | 통합 엑셀(관련 Task)·재입고 알림(관련 Task)이 옵션코드 사용 |

## 9. 정책 검토 항목

| 항목 | 결정 | 정리 위치 |
|---|---|---|
| 정의·단위 | 기존 판매 단위 번호 노출, 재고 행 1개 = 코드 1개 | 정책서 4.1 |
| 형식·번호 | `M{상품번호}-{순번}`, 9자리, 지운 번호 재사용 없음, 상품 안에서 이어 씀 | 정책서 4.2 |

| 미결정 | 번호 채번 단위·복사 상품, 재사용 방지 방법, 비정상 데이터, Open API 필드, 상점 전용 항목 | 사양 정의서 12장 |
