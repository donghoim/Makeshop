## 2. 배경과 문제

| 항목 | 내용 |
|---|---|
| 배경 | 고객이 실제로 사는 것은 상품이 아니라 "블랙 티셔츠 XS"처럼 옵션이 정해진 판매 단위입니다. 판매 단위마다 내부 번호(판매 단위 번호)가 이미 있고, 옵션 없음·미조합 상품도 1개씩 있습니다. 네이버페이·Open API도 이 번호를 씁니다. |
| 해결할 문제 | 운영자가 이 번호를 볼 수 없어 판매 단위를 코드로 가리킬 수 없습니다. 가장 큰 번호의 옵션을 지우면 그 번호를 다시 쓰고, 옵션 사용 안 함으로 바꾸면 1번을 다시 써서 같은 번호가 다른 옵션을 가리킬 수 있습니다. |
| 사용자·운영 영향 | 재고, 재입고 알림처럼 옵션을 번호로 기억하는 기능의 연결이 끊기거나 다른 옵션에 잘못 연결될 수 있습니다. 후속 과제인 통합 엑셀(관련 Task)과 재입고 알림(관련 Task)은 바뀌지 않는 식별자가 먼저 있어야 진행할 수 있습니다. |
| 확인 근거 | 개발 검토 관련 Task(2026-11-05), 개발 검토 회의(2026-11-10), 관련 Task 개발 답변(2026-11-12), demoshop01 관리자 화면 확인(2026-10-29) |

## 3. 목표와 범위

### 3.1 목표

- 판매 단위마다 이미 있는 번호를 옵션코드로 보여 줍니다. 새 번호 체계를 만들지 않습니다.
- 같은 판매 단위는 옵션을 수정·재조합해도 같은 코드를 유지합니다.
- 한 번 쓴 번호는 다른 판매 단위에 다시 쓰지 않습니다.

### 3.2 포함 범위

- 옵션코드 형식(`M{상품번호}-{순번}`), 유지·새 부여·종료 기준
- 재조합 확인창을 버튼 3개(기존 데이터 유지·초기화·취소) 레이어 팝업으로 변경(특별처리 상점 제외)
- 상품 복사·삭제·복구 시 처리
- 옵션 팝업 3종, 상품 수정 요약 박스, 재고 일괄 관리 옵션별 재고 수정 팝업의 읽기 전용 표시
- 전체 상품 관리·삭제 상품 조회·재고 일괄 관리의 옵션코드 검색
- Open API 옵션코드 조회
- 특별처리 상점의 기존 노출 항목 정리

### 3.3 제외 범위

- 상품 엑셀 업로드·다운로드(통합 엑셀 프로젝트 관련 Task 소관, CON-002)
- 재입고 알림 관리의 옵션코드 검색(신청 내역에 번호가 저장되지 않아 구매자 상품 상세까지 개발 필요)
- 다중 상품 옵션 불러오기로 가져온 옵션(현행 동작 유지)
- 관리자앱의 옵션코드 노출·검색
- 주문 메뉴의 옵션코드 검색·표시(추후 업데이트)
- Open API로 옵션코드 수정, 개별옵션 재조합 시 순서 값 오류(관련 Task과 함께 후속 진행), 기존 주문 데이터
