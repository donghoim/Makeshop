# MakeShop MCP — 인증 및 권한(Scope) 정책

> 본 문서는 "MakeShop MCP 연동 서비스 기획안"과 "OAuth 인증 아키텍처 결정안"을 근거로 작성했습니다.
>

## 1. 배경

메이크샵 MCP는 메이크샵 본사 운영자나 슈퍼어드민이 사용하는 기능이 아니라, 메이크샵을 이용하는 **개별 입점사 운영자**가 자신이 운영하는 상점의 데이터를 외부 AI 서비스에서 조회하기 위해 사용하는 기능입니다. 외부 AI 서비스가 메이크샵 데이터를 조회하려면, 누가 요청하는지(사용자 인증), 어느 상점의 데이터인지(상점 식별), 어디까지 조회할 수 있는지(권한 범위)를 연결 시점에 먼저 확정해야 합니다. 인증되지 않은 요청이나 사용자가 동의하지 않은 범위의 데이터, 또는 다른 입점사의 데이터가 AI에게 노출되면 안 되므로, 연결 과정에서 인증·상점 식별·권한 동의 세 단계를 반드시 거치도록 정책으로 규정합니다.

## 2. 목적

이 정책의 목적은 다음과 같습니다.

- 인증되지 않은 주체의 메이크샵 데이터 접근을 차단합니다.
- 사용자가 명시적으로 동의한 데이터 범위 내에서만 AI가 데이터를 조회하도록 합니다.
- 하나의 계정이 여러 상점을 관리하는 경우에도 상점 간 데이터가 섞이지 않도록 합니다.
- 표준 OAuth 구조를 따라 외부 AI 서비스(MCP Client)와 안전하게 연동할 수 있도록 합니다.

## 3. 정책

### 3-1. 기본 인증 방식 [확정]

메이크샵 MCP 연결 시 사용자를 인증하는 기준을 정합니다.

| 항목 | 내용 |
|---|---|
| 인증 방식 | 메이크샵 기존 입점사 관리자 계정 로그인 체계를 재사용합니다. MCP 전용 별도 계정·비밀번호는 생성하지 않습니다 |
| 인증 주체 | 메이크샵이 직접 인증을 수행합니다 |
| 연결 시작 경로 | 사용자가 ChatGPT 등 외부 AI 서비스에서 MakeShop MCP 연결을 시작하면, 메이크샵 로그인 화면으로 이동해 기존 관리자 계정으로 인증합니다 |
| 기존 로그인 세션 | 메이크샵 로그인 세션이 이미 유효한 경우 해당 인증 상태를 재사용할 수 있습니다. 다만 로그인 세션이 유효하더라도 MCP Scope 동의 단계(3-3)는 항상 별도로 진행합니다. 로그인 상태와 MCP 연결 권한은 서로 다른 개념으로 관리합니다 |
| 인증 실패 시 | 로그인에 실패하면 연결을 진행하지 않고, AI 서비스로 복귀시켜 재시도를 안내합니다 |

### 3-2. OAuth 구조 [확정]

MCP 연결의 인가(Authorization) 절차가 따르는 표준 구조입니다.

| 항목 | 내용 |
|---|---|
| 기본 방식 | OAuth 2.x 기반 Authorization Code 방식을 기준으로 설계합니다 |
| Authorization Server 역할 | 메이크샵이 MCP 연결 과정의 인증·권한 동의를 처리하는 Authorization Server 역할을 수행합니다 |
| 기존 인증 시스템과의 관계 | 기존 메이크샵 로그인 인증은 그대로 재사용하되, MCP 외부 연동용 OAuth Authorization 계층은 **별도로 신규 구축**합니다. 기존 로그인 시스템을 그대로 OAuth Server로 확장하지 않고 역할을 분리합니다(개발 리뷰 A-2에서 확정) |
| PKCE | PKCE(Proof Key for Code Exchange) 적용을 기본 전제로 합니다 |

### 3-3. 상점 식별과 연결 단위 [확정]

**MCP 연결 단위는 상점입니다.** 연결 1건은 특정 입점사의 특정 상점 1개에 귀속되며, 계정 단위로 연결되지 않습니다.

| 항목 | 내용 |
|---|---|
| 연결 단위 | 상점입니다. 연결 1건 = 상점 1개이며, 하나의 연결로 여러 상점을 오가며 조회할 수 없습니다 |
| 대상 상점 수 확인 | 로그인한 계정이 관리하는 상점이 1개인지 여러 개인지 먼저 확인합니다 |
| 복수 상점 계정 | MCP 연결 과정에서 접근 가능한 상점 목록을 보여주고, 연결할 상점 1개를 사용자가 직접 선택하도록 합니다. 이 상점 목록은 메이크샵이 제공하는 내부 API(로그인 사용자가 접근 가능한 상점 목록 조회 API)로 조회합니다(개발 리뷰 A-5에서 확정) |
| 단일 상점 계정 | 상점이 1개뿐이면 선택 단계 없이 해당 상점을 자동으로 지정합니다 |
| 선택 시점 | 로그인 직후, Scope 동의(3-4) 이전에 상점을 선택합니다 |
| 다른 상점 데이터가 필요한 경우 | 기존 연결에서 상점을 전환하는 기능은 두지 않으며, 해당 상점에 대한 **별도의 MCP 연결을 새로 생성**해야 합니다 |
| 데이터 범위 | AI 서비스에서 조회되는 주문/상품/회원/매출 데이터는 그 연결에 귀속된 상점의 데이터로 항상 제한됩니다 |

**연결을 상점 단위로 못 박은 이유**: 계정 단위로 연결하고 대화 중 상점을 전환하는 방식은, "이번 주 주문 알려줘" 같은 질문에서 AI와 사용자 모두 어느 상점을 기준으로 묻는 것인지 매번 확인해야 하는 모호함을 만듭니다. 연결 자체를 상점에 귀속시키면 이 모호함이 구조적으로 발생하지 않습니다.

### 3-4. 권한 동의 (Scope 동의) [확정]

MCP 연결 시 AI가 접근할 수 있는 데이터 범위를 사용자에게 안내하고 동의를 받는 기준을 정합니다.

| 항목 | 내용 |
|---|---|
| 동의 시점 | 상점 식별(3-3) 이후, Authorization Code 발급 이전에 동의를 받습니다 |
| 동의 방식 | 요청되는 Scope 목록을 사용자에게 보여주고, 사용자가 명시적으로 동의해야 다음 단계(Authorization Code 발급)로 진행됩니다 |
| 동의 단위 | Scope 4종(3-5) 단위로 개별 동의를 받는 것을 원칙으로 하며, 세부 단위(예: Scope 내 일부 필드만 동의)는 1차 MVP에서 지원하지 않습니다 |
| 매핑 원칙 | Scope와 Tool은 최소 권한 원칙에 따라 매핑합니다(3-6) |
| 미동의 시 처리 | 특정 Scope에 동의하지 않으면 그 Scope에 속한 Tool은 호출할 수 없으며, 동의한 Scope의 Tool만 정상 제공됩니다 |
| 동의 철회 | 사용자가 특정 Scope를 철회하면 해당 Scope에 매핑된 Tool은 즉시 사용 불가 처리합니다. 연결을 해제하면 전체 Scope 동의가 함께 철회됩니다(3-8) |
| 미동의 시 안내 문구 | AI가 미동의 Scope에 속한 Tool을 호출하면 "{데이터 영역}을 조회하려면 {Scope명} 권한이 필요합니다. 연결 설정에서 권한을 추가해 주세요." 형태로 안내합니다. 예: 회원 통계 조회 시도 → "회원 정보를 조회하려면 members.read 권한이 필요합니다. 연결 설정에서 권한을 추가해 주세요." |

다국어 지원은 1차 MVP 범위에 포함하지 않으며, 안내 문구는 한국어만 제공합니다.

### 3-5. 권한 Scope 정의 [확정]

1차 MVP에서 제공하는 조회 전용 Scope 4종의 정의입니다. 실행형(쓰기) Scope는 본 정책의 범위에 포함하지 않습니다.

| Scope | 조회 가능 데이터 |
|---|---|
| `orders.read` | 주문 목록, 주문 건수, 주문 상태, 결제 금액, 결제수단, 취소/반품/교환 상태 |
| `products.read` | 상품명, 상품번호, 판매가, 재고, 판매 상태, 카테고리, 옵션 — 상품 자체의 마스터 정보만 포함하며 판매 실적(수량·매출)은 포함하지 않습니다 |
| `members.read` | 전체 회원 수, 신규 회원 수, 회원 등급, 가입일, 가입 경로 — 이름·전화번호·이메일 등 개별 회원 식별정보는 이 Scope로도 제공하지 않으며, 항상 통계·목록 수준으로만 제공합니다 |
| `analytics.read` | 매출, 주문 건수, 객단가, 취소 금액, 환불 금액, 기간별 증감, 상품별 판매수량·주문건수·매출액, 기간별 판매 순위·기간 비교 실적 |

`products.read`와 `analytics.read`는 "상품이 무엇인가(마스터 정보)"와 "상품이 얼마나 팔렸는가(실적 데이터)"로 경계를 나눕니다. 이렇게 나누면 권한 동의 화면에서도 의미가 명확해집니다. 예를 들어 사용자가 `products.read`만 허용하면 "현재 어떤 상품이 있는지"는 조회할 수 있지만, "이번 달 어떤 상품이 얼마나 팔렸는지" 같은 실적 데이터는 조회할 수 없는 구조가 됩니다.

### 3-6. Tool과 Scope의 매핑 [확정]

각 MCP Tool은 정확히 하나의 Scope에 속하며, 사용자가 해당 Scope에 동의해야만 해당 Tool을 호출할 수 있습니다.

| Scope | 속한 Tool |
|---|---|
| `orders.read` | `get_orders`, `get_order_detail`, `get_order_summary` |
| `products.read` | `get_products` |
| `members.read` | `get_members`, `get_member_summary` |
| `analytics.read` | `get_sales_summary`, `get_product_sales` |

`get_product_sales`(상품별 판매 실적 조회)는 `products.read`가 아니라 `analytics.read`에 속합니다. 이 Tool이 조회하는 핵심 값은 상품 마스터 정보가 아니라 기간별 판매수량·주문건수·매출액이기 때문입니다. 응답에 상품명이 함께 포함되더라도, 이는 결과를 식별하기 위한 부가 정보일 뿐 Tool의 본질은 분석 데이터 조회입니다.

### 3-7. Token 정책 [확정 — 개발/보안 리뷰 완료]

인증·권한 동의가 끝나면 발급되는 Token의 종류와 만료·귀속 기준을 정합니다.

| 항목 | 내용 |
|---|---|
| Token 종류 | Access Token과 Refresh Token을 사용합니다 |
| Access Token 유효기간 | 1시간(3,600초). 만료되면 Refresh Token으로 갱신합니다 |
| Refresh Token Idle 만료 | 마지막 사용일로부터 **30일**간 미사용 시 만료됩니다 |
| Refresh Token 절대 만료 | 발급일로부터 **180일**이 지나면, 미사용 여부와 관계없이 만료되어 재로그인이 필요합니다 |
| Refresh Token Rotation | Access Token을 갱신할 때마다 Refresh Token도 함께 재발급(1회성 사용)하며, 이전 Refresh Token은 즉시 무효화합니다 |
| 재사용(탈취) 탐지 | 이미 무효화된 Refresh Token이 다시 사용되면 탈취 의심으로 간주해 해당 연결의 모든 Token을 즉시 revoke하고 재인증을 요구합니다(3-11 보안 기본 원칙과 연동) |
| Token 귀속 기준(귀속 키) | `user_id` + `shop_id` + `client_id` + `scopes` 조합으로 귀속됩니다 |
| Token 저장 | HTTPS로만 전송하며, 저장 시 암호화합니다 |
| 다상점 연결 시 | 동일한 사용자가 여러 상점을 연결하는 경우, 상점별로 별도의 Token 관계를 가집니다(3-3의 연결 단위 원칙과 일치) |

Access Token 1시간, Rotation·재사용 탐지 적용은 원안대로 승인되었습니다. Refresh Token 만료시간은 최초 제안(Idle 90일/절대 1년)에서 개발/보안 리뷰를 거쳐 **Idle 30일/절대 180일**로 수정 확정되었습니다(09_Meeting/2026-09-22_개발-보안-리뷰요청.md T-2).

### 3-8. 연결 해제 및 Token revoke [확정 — 개발/보안 리뷰 완료]

사용자가 MCP 연결을 해제할 때의 처리 기준입니다.

| 항목 | 내용 |
|---|---|
| revoke 대상 | 연결을 해제하면 해당 연결에 발급된 Access Token과 Refresh Token을 더 이상 사용할 수 없도록 revoke(무효화) 처리합니다 |
| revoke 범위 | 연결 해제는 해당 **상점 연결 건에만** 적용합니다. 같은 사용자의 다른 상점에 대한 별도 MCP 연결에는 영향을 주지 않습니다 |
| 즉시 revoke 트리거 | 아래 5가지 상황에서 Token을 즉시 폐기합니다: ① 사용자가 연결 해제, ② 대표 관리자 권한 상실, ③ 계정 이용정지/탈퇴, ④ Refresh Token 재사용 탐지(3-7), ⑤ 보안 관리자의 강제 해제 |

### 3-9. Scope 변경 시 처리 [확정 / 일부 확인 필요]

Scope가 추가되거나 철회될 때의 처리 기준입니다.

| 항목 | 내용 |
|---|---|
| Scope 추가 | 기존 연결에서 새로운 Scope가 추가되는 경우 사용자 재동의를 받아야 합니다 |
| Scope 철회 | 사용자가 Scope를 철회한 경우 해당 Scope에 매핑된 Tool은 즉시 사용 불가 처리합니다(3-4) |
| Token 처리 | Scope 변경 시 기존 Token을 그대로 사용할지 재발급할지는 [확인 필요]입니다(§10) |

### 3-10. 관리자 권한 [확정 — 개발/보안 리뷰 완료]

MCP 연결이 가능한 관리자 범위를 정합니다.

| 항목 | 내용 |
|---|---|
| 기본 원칙 | MCP 연결 가능 여부는 기존 메이크샵 관리자 권한 체계를 기반으로 판단합니다 |
| 1차 MVP 허용 범위 | **대표 관리자만** MCP 연결을 허용합니다. 부운영자(직원 계정)의 MCP 연결은 1차 MVP 범위에서 제외합니다 |
| 판정 방법 | MCP 연결 시도 시 로그인한 계정이 해당 상점의 대표 관리자 계정인지 확인합니다 |
| 부운영자 계정으로 연결 시도 시 | 연결을 진행하지 않고 "MCP 연결은 대표 관리자 계정만 가능합니다" 형태의 안내를 반환합니다 |
| 복수 대표 관리자 | 한 상점에 대표 관리자 계정이 여러 개 존재하는 경우, 각 대표 관리자가 독립적으로 별도의 MCP 연결을 생성할 수 있습니다. 이 경우 같은 상점에 여러 연결이 동시에 존재하게 되며, 연결 목록을 어떻게 구분·관리할지는 [확인 필요]입니다(§10) |
| 향후 확장 | 부운영자까지 허용하는 확장은 기존 관리자 메뉴 권한과 MCP Scope 간 권한 정합성이 검증된 이후 2단계 이후 별도 정책으로 재검토합니다 |

1차 MVP를 대표 관리자로 좁힌 이유는, MCP가 상점의 주문·회원·매출 데이터 전반에 접근하는 새로운 외부 연동 경로이기 때문입니다. 부운영자별 메뉴 권한과 MCP Scope 간 매핑이 검증되지 않은 상태에서 부운영자 연결을 허용하면, 부운영자가 기존 메뉴 권한으로는 볼 수 없던 데이터를 MCP를 통해 우회 조회할 위험이 있습니다.

### 3-11. 보안 기본 원칙 [확정]

MCP 인증·연결 과정 전반에 적용하는 보안 원칙입니다.

| 항목 | 내용 |
|---|---|
| 통신 | HTTPS 기반 통신을 전제로 합니다 |
| Authorization Code | 1회성으로만 사용합니다 |
| PKCE | 기본으로 적용합니다(3-2) |
| Token 저장/전송 | HTTPS로만 전송하며, 저장 시 암호화합니다(3-7) |
| Token 노출 금지 | Token은 로그 및 화면에 원문으로 노출하지 않습니다 |
| 탈취 대응 | Token 탈취·유출이 의심되면 즉시 revoke할 수 있는 구조를 제공합니다 |
| 매 호출 검증 | MCP 요청이 올 때마다 Token 유효성, 상점 ID, Scope를 검증합니다 |
| 상점 Context 강제 | 상점 컨텍스트는 Token에 귀속된 `shop_id`를 서버가 강제로 사용하며, AI Client가 파라미터로 상점을 임의 지정하는 구조는 허용하지 않습니다 |
| Scope 이중 검증 | MCP Server가 Tool 실행 전 1차로 Scope를 검증하고, 메이크샵 내부 API 호출 시점에 상점 접근 권한을 다시 검증합니다 |

## 4. 우선순위

연결 및 Tool 호출 시 아래 순서로 조건을 확인하며, 앞 단계에서 실패하면 뒤 단계로 진행하지 않습니다.

| 순서 | 확인 항목 |
|---|---|
| 1 | 인증(로그인) 성공 여부 |
| 2 | 상점 식별 완료 여부 |
| 3 | Token 유효성(만료·revoke 여부) |
| 4 | 호출하려는 Tool이 속한 Scope의 동의 여부 |

## 5. 예외

- 계정이 상점을 1개만 보유한 경우 상점 선택 단계를 생략하고 자동으로 해당 상점을 지정합니다(3-3).
- 대표 관리자가 아닌 부운영자(직원) 계정은 1차 MVP에서 MCP 연결을 허용하지 않습니다(3-10).

## 6. 운영

- 신규 Scope를 추가하는 경우, 기존에 연결된 사용자에게 재동의를 요구합니다(3-9).
- Scope의 정의(포함 데이터 범위) 자체를 변경하는 경우, 사전 공지 후 반영하는 것을 원칙으로 합니다. [제안] 구체적인 공지 방식과 시점은 [확인 필요]입니다.
- Token 탈취·유출이 의심되는 경우 즉시 revoke를 수행합니다(3-11).

## 7. 권한

본 정책(인증 방식, OAuth 구조, 상점 식별 방식, Scope 정의, Token 정책, 동의 절차)을 설정·변경할 수 있는 주체는 [확인 필요]입니다. 서비스 기획과 개발/보안 조직의 협의가 필요합니다.

## 8. 로그

- 인증 성공/실패 이력
- Scope 동의/철회 이력
- 상점 선택 이력
- Token 발급·갱신·revoke 이력

MCP Tool 호출 자체에 대한 로그(호출 Tool, 호출 일시, 조회 데이터 범위, 처리 결과 등)는 본 정책이 다루는 범위가 아니며, 별도의 로그·예외처리 정책이 다룹니다.

## 9. 이력

정책 변경 이력은 본 문서에 직접 기록하지 않습니다. 본 문서에는 항상 최신 확정 내용만 반영합니다.
