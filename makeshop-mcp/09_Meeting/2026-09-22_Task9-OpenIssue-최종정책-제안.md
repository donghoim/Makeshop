# 2026-09-22 논의 — Task 9 Open Issue 최종 정책 제안 (4건)

> 아래 4건은 서비스 기획이 업계 표준 관행과 기존 확정 정책을 근거로 작성한 **제안안**입니다. 수치·산식의 최종 확정에는 개발/보안 조직의 검증이 필요하므로, 정책 문서에는 `[제안]`으로 반영합니다.

## 1. Token 만료시간 및 재인증 정책

### 결정안

| 항목 | 값 |
|---|---|
| Access Token 유효기간 | 1시간(3,600초) |
| Refresh Token Idle 만료(미사용 시) | 마지막 사용일로부터 90일 |
| Refresh Token 절대 만료(Absolute lifetime) | 발급일로부터 1년(1년 경과 시 재로그인 필요) |
| Refresh Token Rotation | Access Token 갱신 시마다 Refresh Token도 함께 재발급(1회성 사용). 이전 Refresh Token은 즉시 무효화 |
| 재사용(탈취) 탐지 | 이미 사용되어 무효화된 Refresh Token이 다시 사용되면 탈취 의심으로 판단, 해당 연결의 모든 Token을 즉시 revoke하고 재인증을 요구 |

### 결정 이유

OAuth 2.1 권장사항(짧은 수명의 Access Token + Rotation이 적용된 Refresh Token)을 따라, Access Token이 유출되더라도 피해 범위를 1시간 이내로 제한합니다. Refresh Token Idle 만료(90일)는 장기 미사용 연결을 자동 정리해 불필요한 노출을 줄이고, 절대 만료(1년)는 탈취된 Refresh Token이 탐지되지 않은 채 무기한 사용되는 것을 방지합니다. Rotation과 재사용 탐지는 05_Policy 인증·권한 정책 3-11(보안 기본 원칙)의 "Token 탈취·유출이 의심되면 즉시 revoke"라는 이미 확정된 원칙을 Token 갱신 흐름에 구체적으로 적용한 것입니다.

### 정책 상세

- 사용자는 Refresh Token이 유효한 90일 동안은 재로그인 없이 자동으로 Access Token을 갱신하며 MCP를 계속 사용할 수 있습니다.
- Refresh Token이 Idle 만료(90일 미사용) 또는 절대 만료(1년)에 도달하면, 다음 Tool 호출 시 `TOKEN_EXPIRED`가 아닌 재인증이 필요한 상태로 처리하고, AI 서비스는 사용자에게 재연결을 안내합니다.
- Token 발급·갱신·revoke 이력은 05_Policy 인증·권한 정책 §8(로그)에 따라 기록합니다.

### 예외사항

- 개발/스테이징 환경에서는 테스트 편의를 위해 더 짧은 만료시간(예: Access Token 5분)을 별도로 적용할 수 있습니다.
- Scope 추가로 재동의가 발생하면(3-9) 새 Token을 발급하며, 이 시점에 만료시간이 다시 시작됩니다.

### 영향 문서

- `05_Policy/01_인증-권한-정책.md` §3-7(Token 정책), §10(미결정사항)

## 2. Rate Limit 기준

### 결정안

| 항목 | 값 |
|---|---|
| 적용 단위 | 상점(연결) 단위 |
| 분당 요청 상한 | 60회 |
| 시간당 요청 상한 | 1,000회 |
| 초과 시 처리 | `RATE_LIMITED` 반환, Response에 `retry_after`(재시도 가능 시점, 초 단위) 포함 |

### 결정 이유

06_Data-API §11-11에서 이미 "MCP는 대량 데이터 추출 또는 반복 호출 용도로 사용하지 않는다"는 목적이 확정되어 있습니다. 복합 분석 시나리오(07_QA QA-COMBO-001, 최대 8회 연속 호출)가 정상적으로 처리되면서도 자동화된 대량 크롤링을 억제할 수 있는 수준으로, 분당 60회(초당 1회 수준)를 기본값으로 설정합니다. 시간당 1,000회는 하루 동안 정상적인 대화형 조회를 반복해도 도달하기 어려운 여유 있는 상한으로, 이상 사용 패턴을 걸러내는 안전판 역할을 합니다. 상점 단위로 적용해 한 상점의 과다 호출이 다른 상점에 영향을 주지 않도록 합니다(05_Policy 개인정보·보안 정책 3-1의 상점 데이터 분리 원칙과 정합).

### 정책 상세

- 분당/시간당 두 기준 중 하나라도 초과하면 `RATE_LIMITED`를 반환합니다.
- `retry_after`는 다음 요청이 허용되는 시점까지 남은 초를 안내합니다.
- Rate Limit 카운트는 Tool 종류와 무관하게 상점 단위로 합산합니다(1차 MVP 기준, Tool별 세분화는 하지 않음).

### 예외사항

- 집계/분석형 Tool(Timeout 15초, §11-9)은 서버 부하가 더 크므로 별도의 낮은 상한을 둘지는 실제 인프라 부하 테스트 후 재검토합니다.
- 위 수치는 실제 트래픽 데이터가 쌓이기 전까지는 잠정치이며, 운영 중 조정될 수 있습니다.

### 영향 문서

- `06_Data-API/MCP-Tools-Definition.md` §11-11(Rate Limit), §12(Open Issues)

## 3. 매출 산식 및 배송비/포인트/취소·환불 반영 기준

### 결정안

| 필드 | 산식 |
|---|---|
| `gross_sales` | 해당 기간 결제완료 주문의 상품 정가 기준 주문금액 합계(배송비 제외, 결제대기/미결제 주문 제외) |
| `discount_amount` | 위 주문에 적용된 상품할인 + 주문할인 + 쿠폰할인의 합계 |
| `canceled_amount` | 취소 승인 완료된 금액의 합계(부분취소는 실제 취소된 금액만 반영) |
| `refunded_amount` | 환불 완료된 금액의 합계(부분환불은 실제 환불된 금액만 반영) |
| `net_sales` | `gross_sales` − `discount_amount` − `canceled_amount` − `refunded_amount` |
| `gross_payment_amount`(선택 반환) | `gross_sales` − `discount_amount` + 배송비 (결제수단·포인트/적립금 사용 여부와 무관하게 실제 결제된 총액) |

### 결정 이유

06_Data-API §9에서 5개 필드로 구분하기로 이미 확정했으나 정확한 계산식이 비어 있었습니다. 커머스 매출 집계의 일반 원칙(총 주문금액 → 할인 차감 → 취소/환불 차감 = 순매출)을 그대로 적용하고, 배송비는 상품 매출과 성격이 다른 부가 항목이므로 기본 매출 지표에서 분리합니다. 포인트·적립금·예치금 등은 "결제수단"일 뿐 판매 자체가 발생한 사실과는 무관하므로, 어떤 결제수단으로 결제되었든 매출 인식(gross_sales/net_sales)에는 동일하게 포함합니다(결제수단 무관 원칙).

### 정책 상세

- 취소/반품/환불은 **처리 완료 시점**이 아니라 **원 주문이 속한 조회 기간**에 소급 반영합니다. 즉 "이번 달 매출"은 이번 달에 생성된 주문 기준으로 집계하되, 그중 이후 시점에 취소·환불된 금액도 조회 시점까지 발생한 것을 모두 반영합니다. 이는 `get_orders`/`get_order_summary`/`get_sales_summary`가 항상 조회 시점 기준 최신 상태를 반환하는 라이브 조회 Tool이기 때문이며, 과거 기간의 `net_sales`는 이후 취소가 발생하면 조회 시점에 따라 달라질 수 있습니다.
- 포인트·적립금 등 비현금성 결제수단 자체의 적립/차감(자산 이동)은 매출 집계 대상이 아니며, MCP는 이를 별도로 집계하지 않습니다.
- 배송비 포함 결제총액이 필요한 질문에는 `gross_payment_amount`를 별도로 제공합니다(§9 기존 결정 유지).

### 예외사항

메이크샵 내부 통계 화면이 이미 별도의 매출 집계 로직·시점 기준(예: 처리시점 기준 집계)을 사용하고 있다면, 본 산식과 값이 일치하지 않을 수 있습니다. 이 경우 본 정책의 산식이 MCP 응답의 기준이며, 기존 통계 화면과의 정합성 여부 확인은 개발 검증이 필요합니다(기존 Open Issue로 유지).

### 영향 문서

- `06_Data-API/MCP-Tools-Definition.md` §9(매출 정의), §12(Open Issues)

## 4. 대표 관리자/부운영자 MCP 연결 허용 범위

### 결정안

1차 MVP에서는 **대표 관리자만** MCP 연결을 허용합니다. 부운영자(직원 계정)의 MCP 연결은 1차 MVP 범위에서 제외합니다.

### 결정 이유

MCP는 상점의 주문·회원·매출 데이터 전반(개인정보·민감정보 제외 후에도 여전히 민감한 경영 데이터 포함)에 접근하는 새로운 외부 연동 경로입니다. 기존 메이크샵 관리자 메뉴 권한 체계와 MCP Scope(4종) 간의 매핑이 아직 검증되지 않은 상태에서 부운영자까지 연결을 허용하면, 부운영자가 기존 메뉴 권한으로는 볼 수 없던 데이터를 MCP를 통해 우회적으로 조회하게 될 위험이 있습니다. 따라서 1차 MVP는 상점에 대해 가장 큰 권한을 가진 대표 관리자로 연결 범위를 좁혀 리스크를 최소화하고, 부운영자별 메뉴 권한과 MCP Scope 간 정합성이 검증된 이후 단계적으로 확장하는 접근을 취합니다.

### 정책 상세

- MCP 연결 시도 시 로그인한 계정이 해당 상점의 대표 관리자 계정인지 확인합니다.
- 부운영자 계정으로 로그인을 시도하면 연결을 진행하지 않고, "MCP 연결은 대표 관리자 계정만 가능합니다" 형태의 안내를 반환합니다.
- 부운영자 지원은 2단계 이후 별도 정책 수립을 통해 확장 여부를 재검토합니다.

### 예외사항

한 상점에 대표 관리자 계정이 여러 개 존재하는 경우(복수 대표 계정을 지원하는 상점), 각 대표 관리자가 독립적으로 별도의 MCP 연결을 생성할 수 있습니다. 이 경우도 연결 단위는 여전히 "상점"이므로(05_Policy 인증·권한 정책 3-3), 같은 상점에 여러 개의 연결이 동시에 존재할 수 있습니다. 이때 연결 목록을 어떻게 구분·관리할지는 [확인 필요]로 신규 등록합니다.

### 영향 문서

- `05_Policy/01_인증-권한-정책.md` §3-10(관리자 권한), §10(미결정사항)
