# MakeShop MCP — 개발 킥오프

> MakeShop MCP 1차 MVP 기획 패키지(요구사항/정책/Data-API/QA)와 개발/보안 리뷰가 모두 완료된 상태에서, 실제 개발 착수를 지원하기 위해 작성한 문서입니다. 세부 스펙의 원본은 각 문서(01_Requirements, 05_Policy, 06_Data-API, 07_QA)이며, 이 문서는 그 내용을 개발 착수 관점에서 재구성한 요약본입니다.

## 1. 개발 목표

메이크샵을 이용하는 개별 입점사의 **대표 관리자**가 ChatGPT 등 MCP Client에서 자연어만으로 자신이 운영하는 상점의 주문/회원/상품/매출 데이터를 조회할 수 있도록, 메이크샵 MCP Server(1차 MVP, 조회형)를 구현합니다.

## 2. MVP 구현 범위 (In-Scope)

- MCP Server 신규 구축 (GPT 등 AI Client는 메이크샵 내부 API를 직접 호출하지 않고 반드시 MCP Server를 거침)
- OAuth 2.x Authorization Code + PKCE 기반 인증/연결 (기존 메이크샵 로그인 재사용 + 신규 OAuth Authorization 계층)
- 상점 단위 연결(연결 1건 = 상점 1개), 대표 관리자만 연결 허용
- Scope 4종: `orders.read`, `products.read`, `members.read`, `analytics.read`
- Tool 8종(§7)
- Access/Refresh Token 발급·갱신·revoke
- Rate Limit, 호출 로그(중앙 Audit Log)
- 개인정보 최소 제공 원칙 적용

## 3. Out-of-Scope

- 실행형(쓰기) Tool 및 `orders.write`/`products.write`/`members.write`/`promotions.write` Scope (Phase 3)
- 여러 Tool을 조합한 자동 분석 로직 자체 (AI Client의 역할이며 메이크샵은 원본 데이터 제공까지)
- 부운영자(직원 계정)의 MCP 연결
- 메이크샵 관리자 내 AI 질의 화면, 연결 관리 화면(§6.2, Phase 2 착수 시점에 재검토)
- CS, 배송, 정산 등 주문/회원/상품/매출 외 도메인의 MCP Tool화
- 메이크샵이 아닌 제3자 커머스 플랫폼과의 MCP 연동
- UI Prototype (10_Prototype 미생성 — 실제 UI는 외부 MCP Client가 제공)

## 4. 핵심 아키텍처

```
GPT 등 AI Client
  ↓
MakeShop MCP Server
  ↓
OAuth 인증 / Scope 검증 (1차, Tool 실행 전)
  ↓
연결된 상점 식별 (Token에 귀속된 shop_id를 서버가 강제 사용)
  ↓
MakeShop 내부 API / 데이터 조회 (2차 상점 접근권한 재검증)
  ↓
MCP Tool Response (서버 집계 결과, Raw 대량 데이터 아님)
  ↓
AI가 사용자에게 결과 제공
```

**아키텍처 원칙**
- AI Client는 상점 컨텍스트를 파라미터로 임의 지정할 수 없습니다. 상점은 항상 Token에 귀속된 `shop_id`로 서버가 결정합니다.
- Scope 검증은 MCP Server(Tool 실행 전)와 메이크샵 내부 API(호출 시점) 양쪽에서 이중으로 수행합니다.
- 기존 메이크샵 API를 우선 재사용하고, Tool이 요구하는 형태(예: 집계값)를 기존 API가 제공하지 못하면 MCP 전용 Aggregation API를 신규로 추가합니다.
- 집계형 Tool은 항상 서버가 이미 집계한 결과를 반환합니다. AI가 목록형 Tool로 대량 Raw 데이터를 받아 직접 합산하도록 설계하지 않습니다.

## 5. 개발 선행조건

구현에 착수하기 전에 확인·준비되어야 하는 항목입니다.

| 항목 | 내용 |
|---|---|
| 상점 목록 조회 API | 로그인 사용자가 접근 가능한 상점 목록을 조회하는 내부 API가 필요합니다(신규 또는 기존 재사용 확인) |
| OAuth Authorization 계층 | 기존 로그인 시스템과 별도로, MCP 전용 OAuth Authorization Server(Consent, Token 발급)를 구축해야 합니다 |
| Token 저장소 | Token을 암호화 저장할 저장소(및 Refresh Token Rotation·재사용 탐지 로직)가 필요합니다 |
| 중앙 Audit Log 시스템 | Tool 호출 로그를 저장할 중앙 Audit Log 연동 지점이 필요합니다 |
| Aggregation API 필요 여부 판단 | `get_order_summary`/`get_sales_summary`/`get_member_summary`/`get_product_sales` 각각에 대해 기존 API로 충족 가능한지, 신규 Aggregation API가 필요한지 Tool별로 사전 판단이 필요합니다 |

## 6. 구현 우선순위 [제안]

| 단계 | 내용 |
|---|---|
| Phase A | 인증/OAuth 기반 구축 — 로그인 연동, Authorization Code+PKCE, 상점 선택, Scope 동의, Token 발급/저장 |
| Phase B | 조회형 Tool 8종 구현(§7 순서 참고) |
| Phase C | 공통 정책 마감 — Rate Limit, Timeout/Retry, 공통 Error 체계, 중앙 Audit Log, revoke 트리거 5종 |
| Phase D | QA 검증 — 07_QA/QA-시나리오.md 65건 실행 및 통과 |

Phase A 없이는 어떤 Tool도 인증·Scope 검증을 통과할 수 없으므로, 인증 기반을 가장 먼저 구축하는 것을 제안합니다.

## 7. Tool 8종 개발 순서 [제안]

Tool 간 패턴(목록/상세/집계)이 반복되므로, 가장 단순한 패턴부터 구현해 이후 Tool에서 재사용하는 순서를 제안합니다.

| 순서 | Tool | 이유 |
|---|---|---|
| 1 | `get_orders` | 목록형 Tool의 기본 패턴(인증/Scope/Cursor Pagination/limit/정렬/keyword)을 확립 |
| 2 | `get_order_detail` | 단일 리소스 조회 패턴(가장 단순) |
| 3 | `get_order_summary` | 집계형 Tool의 기본 패턴(기간 기본값/최대값, `order_status` 조건 포함) 확립 |
| 4 | `get_products` | 목록형 패턴 재사용 + `min_stock`/`max_stock` 조건 검증 |
| 5 | `get_members` | 목록형 패턴 재사용 + 개인정보 필드 제외 로직(3-5 표) 검증 |
| 6 | `get_member_summary` | 집계형 패턴 재사용 + `member_grade` 조건 |
| 7 | `get_sales_summary` | 매출 산식(§9) 적용 — 가장 로직이 복잡하므로 목록/집계 패턴이 안정된 뒤 구현 |
| 8 | `get_product_sales` | 매출 산식 재사용 + `analytics.read` Scope 적용(products.read 아님에 유의) |

## 8. 인증/OAuth 의존성

| 항목 | 내용 |
|---|---|
| 인증 방식 | 기존 메이크샵 관리자 로그인 재사용, MCP 전용 계정 없음 |
| OAuth 구조 | Authorization Code + PKCE, 메이크샵이 Authorization Server 역할 |
| 연결 대상 | 대표 관리자만(부운영자 연결 거부 필요) |
| 연결 단위 | 상점 단위(연결 1건 = 상점 1개), 전환 기능 없이 별도 연결 생성 |
| Access Token | 1시간 |
| Refresh Token | Idle 30일 / 절대 180일, Rotation 적용(갱신마다 재발급, 이전 것 즉시 무효화) |
| 재사용 탐지 | 무효화된 Refresh Token 재사용 시 해당 연결 전체 Token revoke + 재인증 요구 |
| Token 귀속 키 | `user_id` + `shop_id` + `client_id` + `scopes` |
| revoke 트리거(5종) | 연결 해제 / 대표관리자 권한 상실 / 계정 이용정지·탈퇴 / Refresh Token 재사용 탐지 / 보안 관리자 강제 해제 |
| Scope 동의 | 4종 Scope 단위 동의, 신규 Scope 추가 시 재동의 |

상세 근거: `05_Policy/01_인증-권한-정책.md`

## 9. 데이터/API 의존성

| 항목 | 내용 |
|---|---|
| 기존 API 재사용 | 우선 재사용하고, 부족한 Tool에는 MCP 전용 Aggregation API 신규 추가 |
| Pagination | 항상 Cursor 방식(`items`/`next_cursor`/`has_more`)으로 노출. 내부 구현이 Page 방식이어도 인터페이스는 Cursor로 추상화 |
| 기간 기준 | 주문 관련은 `order_created_at` 기준. Timezone은 상점 설정 우선(기본 `Asia/Seoul`) |
| 기본/최대 조회기간 | 집계형 Tool 4종: 기본 7일, 최대 90일 |
| limit | 목록형 Tool 4종: 기본 50, 최대 100(자동 보정 없이 `LIMIT_EXCEEDED`) |
| 신규 필터 파라미터 | `get_order_summary`에 `order_status`, `get_products`에 `min_stock`/`max_stock`, `get_member_summary`에 `member_grade` 추가 필요 |
| 매출 산식 | `net_sales = gross_sales - discount_amount - canceled_amount - refunded_amount`. **구현 시 메이크샵 관리자 통계 화면과 동일 산식 사용이 전제**이며, 실제 수치 일치 여부는 구현 단계에서 최종 검증 필요(§14) |
| 서버 집계 원칙 | AI가 Raw 데이터를 직접 합산하지 않도록, 집계형 Tool은 항상 서버 집계 결과를 반환 |

상세 근거: `06_Data-API/MCP-Tools-Definition.md`

## 10. 보안 필수사항

| 항목 | 내용 |
|---|---|
| 통신 | HTTPS 전제 |
| Authorization Code | 1회성 |
| PKCE | 기본 적용 |
| Token 저장/전송 | HTTPS 전송, 저장 시 암호화 |
| Token 노출 금지 | 로그·화면에 Token 원문 노출 금지 |
| 상점 Context | Token 기준 강제(Client가 `shop_id` 임의 지정 불가) |
| Scope 검증 | MCP Server + 내부 API 이중 검증 |
| Rate Limit | `shop_id`+`client_id` 기준, 분당 60회/시간당 1,000회, 초과 시 `RATE_LIMITED`+`retry_after` |
| 로그 | 중앙 Audit Log 저장, Token 원문·직접식별 개인정보 미기록 |
| 개인정보 제공 범위 | 이름/전화번호/이메일/주소/계좌정보/인증정보 전부 미제공(마스킹 없음). `member_id`는 불투명 내부 식별자 |
| 개인정보 처리 동의 | MCP 최초 연결 시 외부 서비스 제공 동의 문구 제공 |

상세 근거: `05_Policy/01_인증-권한-정책.md` §3-11, `05_Policy/02_개인정보-보안-정책.md`

## 11. QA 연계 방식

- `07_QA/QA-시나리오.md`(17개 영역, 65건)를 구현 검증의 기준 시나리오로 사용합니다.
- Tool 또는 기능 단위 구현이 완료될 때마다, 해당 영역의 QA 케이스(예: `get_orders` 구현 완료 시 QA-SINGLE-001, QA-COND-001/002 등)를 실행합니다.
- 정상/예외/Boundary/Permission/Regression 5개 유형이 실제로 모두 검증되는지 확인합니다.
- QA 진행 중 시나리오와 실제 구현이 불일치하는 경우(예: 산식·파라미터 차이), 시나리오를 임의로 수정하지 않고 PM에게 먼저 공유합니다(§12).

## 12. 개발 중 PM 확인이 필요한 항목

아래 상황이 발생하면 기획 문서를 임의로 해석하지 않고 PM(서비스 기획)에게 먼저 공유합니다.

- Tool 스펙에 정의되지 않은 파라미터·필드가 필요한 것으로 판명된 경우 (과거 사례: `get_order_summary`의 `order_status` 필터 등 3건이 이런 방식으로 발견·반영됨)
- 매출 산식이 메이크샵 관리자 통계 화면과 실제로 불일치하는 것으로 확인된 경우
- 기존 메이크샵 API가 요구 스펙(Cursor Pagination, 90일 조회, 특정 필터 등)을 충족하지 못해 설계 변경이 필요한 경우
- 남은 Non-Blocking Open Issue(§14)가 실제 구현을 막는 수준으로 판명된 경우
- 보안/개인정보 정책(05_Policy)에 명시되지 않은 새로운 데이터 노출 케이스를 발견한 경우

## 13. 완료 조건 (Definition of Done)

- [ ] Tool 8종이 각자의 소속 Scope 검증과 함께 정상 동작
- [ ] 인증/연결 Flow(로그인 → 상점 선택 → Scope 동의 → Authorization Code → Token 발급 → AI 서비스 복귀)가 정상 동작
- [ ] Access/Refresh Token 발급·Rotation·재사용 탐지·revoke(5종 트리거)가 정상 동작
- [ ] `07_QA/QA-시나리오.md`의 65건이 모두 통과(또는 사유가 기록된 채 보류)
- [ ] Rate Limit(shop+client 기준), Timeout(10초 통일), Retry(최대 1회) 정책이 반영됨
- [ ] `05_Policy/02_개인정보-보안-정책.md` §3-5 표 기준으로 Tool 응답에 개인정보 필드가 없음을 검수 완료
- [ ] Tool 호출 로그가 중앙 Audit Log에 기록되고, Token/개인정보 원문이 로그에 없음을 확인
- [ ] MCP 최초 연결 시 개인정보 처리 동의 문구가 노출됨

## 14. 남은 Non-Blocking Open Issue

아래 9건은 **개발 착수를 막지 않는** Non-Blocking 항목입니다. 핵심 아키텍처·정책은 개발/보안 리뷰에서 이미 승인되었으므로, 아래 항목은 구현을 진행하면서 병행 확인하거나 별도 트랙에서 정리합니다.

| 번호 | 항목 | 구분 | 확인 필요 대상 |
|---|---|---|---|
| 1 | 한 상점에 대표 관리자가 여러 명인 경우 여러 MCP 연결을 어떻게 구분·관리할지 | 개발 | 정책/개발 |
| 2 | Response 필드명(영문 snake_case 등)의 최종 확정 | 개발 | 개발 |
| 3 | 결제수단명(제공)과 결제수단 원문 정보(미제공)의 필드 단위 경계 | 개발 | 개발 |
| 4 | 매출 산식이 실제 구현 시 메이크샵 관리자 통계 화면과 수치가 정확히 일치하는지 최종 검증 | 개발 | 개발 |
| 5 | Scope 변경 시 기존 Token을 재사용할지 재발급할지 | 개발/보안 | 개발/보안 |
| 6 | 운영자 본인의 개별 회원 개인정보 열람 예외 허용 여부 | 보안/법무 | 법무 |
| 7 | 극소수 인원 재식별 가능성 처리 기준 | 보안/법무 | 법무 |
| 8 | 로그 보관 기간 | 보안/법무 | 법무 |
| 9 | 개인정보 처리 동의 문구의 정확한 문안 | 보안/법무 | 법무 |

> 참고: 항목 2·3(Response 필드명, 결제수단 필드 경계)은 구현 과정에서 자연스럽게 확정되는 세부사항이며, 항목 1·5(복수 연결 관리, Scope 변경 시 Token 처리)는 MVP 초기 사용 패턴에서는 발생 빈도가 낮아 구현을 막지 않습니다. 항목 6~9(법무)는 서비스 약관·개인정보처리방침 게시와 함께 별도 트랙에서 진행하며, 개발 착수와 병렬로 진행 가능합니다.
